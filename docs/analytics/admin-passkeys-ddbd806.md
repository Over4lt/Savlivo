### Registration

Registration requires an existing credential-authenticated admin session or an operator-issued enrollment-only grant. Customer JWTs, client role claims and old password sessions cannot authorize it. There is no public role assignment or grant-issuance endpoint.

An operator grant is 32 cryptographically random bytes with the existing adm_ prefix. Only its SHA-256 hash is stored. It expires after five minutes, is bound to the configured origin and can only begin one registration. It cannot read the overview or become an admin login session. Grant consumption and challenge creation are one transaction. A failed native registration requires a new grant (or a new options request from an authenticated session).

Registration challenges are generated by the verifier, stored server-side with purpose, owner, exact RP/origin, five-minute expiry and a revocable enrollment version. Existing-session enrollment also references the authorizing session, so logout/deletion invalidates it. An operator's replacement grant, revoke-all or completed enrollment rotates the enrollment version, preventing even a previously consumed/in-flight registration from surviving revocation. The browser is given a generic display name and a separate random WebAuthn user handle, not the internal account UUID or email.

Options exclude existing credentials for the account/RP and cap enrollment at 20 credentials per account/RP (operator removal is required before adding more). Options require discoverable credentials and user verification; no device-specific attestation is requested. The server requires user presence and verification and validates the exact challenge, origin and RP ID using SimpleWebAuthn. Cross-origin/top-origin assertions are rejected. Credential IDs are unique; conflicting IDs cannot reassign ownership. Registration stores the public key, credential ID, owner, RP ID, counter and creation time. It never stores a private key, raw assertion/attestation or credentials copied from provider pages. No transport/name/fingerprint metadata is retained. Registration does not issue a login session, and success revokes prior admin sessions.

### Authentication, RBAC and sessions

Authentication uses fresh five-minute discoverable-credential challenges, with no email or account enumeration. Challenge consumption commits before verification, including on failed assertions. The signed response must match exact origin/RP/challenge, user presence/verification, known credential, signature and the account's WebAuthn user handle. User identity comes from the credential's server-side FK, never a supplied role/user ID. A live role and non-pending-deletion account are required before issuance.

Account/role and credential locks serialize counter checks and issuance. Nonzero counters must increase; repeated/lower values fail. Zero counters remain valid for authenticators that do not maintain a counter; single-use random challenges still prevent assertion replay. This does not guarantee cloned synced credentials can be detected. See [official passkey guidance](https://simplewebauthn.dev/docs/advanced/passkeys).

Only verified authentication issues a 256-bit random token with a 15-minute absolute expiry; only its SHA-256 hash is persisted. Counter update, session insertion and session-created audit are atomic. Audit failure rolls back issuance; the challenge remains consumed. Every privileged request checks the active DB role, account deletion state, credential ownership/RP and unexpired credential-linked session.

Logout deletes the current session before its audit write. Revoke-all serializes with issuance, rotates enrollment version and deletes all sessions/pending enrollments before auditing; a failed audit cannot restore access. Credential deletion cascades linked sessions; public-key/owner/RP replacement triggers session deletion. Role/account deletion cascades credentials/sessions. An in-flight read already authorized before revocation cannot be recalled. A stolen valid session remains replayable until revocation or its 15-minute expiry. No device fingerprint, idle timeout or token rotation was introduced.

Password admin login is removed in **all runtimes**, including localhost. There is no password recovery bypass. Customer password reset does not authenticate admin and is not a passkey recovery mechanism. A lost passkey requires an independently authorized operator recovery procedure, not a normal customer password login.

### HTTP and client

Routes (all remain behind explicit non-production admin configuration and exact Origin checks):

- POST `/v1/admin/passkeys/register/options`: existing passkey session or enrollment-only bearer grant; empty object body.
- POST `/v1/admin/passkeys/register/verify`: challengeId plus native registration response.
- POST `/v1/admin/passkeys/authenticate/options`: empty object body.
- POST `/v1/admin/passkeys/authenticate/verify`: challengeId plus native assertion.
- DELETE `/v1/admin/session`: logout.
- DELETE `/v1/admin/sessions`: revoke all current admin sessions and pending enrollments.

There is no password POST session route, credential export, role API or public operator-bootstrap API. Four passkey routes have strict outer fields, 32 KiB bodies, generic errors and bounded per-process abuse limits (30/IP/minute and 120 total/minute). IP is transient memory only; forwarded headers are not trusted. These are not distributed rate limits. Existing read/audit/CORS/no-store/nosniff/referrer/frame/CSP/Permissions-Policy protections remain.

The client offers sign-in, registration, logout and revoke-all. Enrollment grants are cleared from the input immediately and sent only in Authorization, not URL/body/storage. Session tokens stay in memory. Browser cancellation creates no session; late results are ignored/revoked; logout aborts pending native requests and clears results. Raw credential material is only serialized transiently for verification and never rendered. Credential removal is intentionally operator-side, not a new account-management UI.

```sql
\prompt 'Approved internal account UUID: ' admin_user_id
\prompt 'Configured/approved audit retention days: ' audit_days
BEGIN;
WITH granted AS (
  INSERT INTO admin_roles(user_id,role)
  SELECT id,'analytics_reader' FROM users
  WHERE id=:'admin_user_id'::uuid AND deletion_scheduled_for IS NULL
  ON CONFLICT(user_id) DO NOTHING RETURNING user_id
)
INSERT INTO admin_audit(user_id,action,expires_at)
SELECT user_id,'role_granted',now()+:'audit_days'::integer*interval '1 day'
FROM granted;
COMMIT;
```
